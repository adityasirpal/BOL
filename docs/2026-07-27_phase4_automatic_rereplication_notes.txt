PHASE 4 OBJECTIVE

Build and validate automatic failover and automatic re-replication when a storage node becomes unavailable.

The system needed to:

1. Detect or simulate a failed node.
2. Identify primary chunks affected by the failed node.
3. Select a valid online replica.
4. Promote that replica to primary.
5. Record a recovery event.
6. Select another eligible online node.
7. Create a replacement replica record.
8. Restore the required replica count.
9. Avoid selecting offline nodes or the failed node.
10. Avoid duplicate endpoints and unnecessary duplicate code.

4. Automatic Failover Improvements

Updated automatic_failover() to process primary chunks stored on the failed node.

For every affected primary chunk, the system:

- Searches distributed_chunk_replicas
- Joins against the nodes table
- Requires the replica node to be online
- Excludes the failed node
- Selects the preferred eligible replica
- Marks the failed primary storage record as failed
- Marks the selected replica as promoted_to_primary
- Creates a recovery event


5. Recovery Event Logging

Each successful promotion creates an entry in recovery_events.

Recorded information includes:

- recovery_id
- file_id
- chunk_id
- failed_node_id
- promoted_node_id
- recovery_action
- status
- created_at

Recovery action used:

automatic_failover

Recovery status used:

recovered


6. Database-Level Automatic Re-Replication

After promoting a replica to primary, the system now searches for another eligible online node to restore redundancy.

The replacement-node selection excludes:

- The failed node
- The newly promoted node
- Nodes already holding an active replica for that chunk
- Offline nodes

A new distributed_chunk_replicas record is then created for the selected replacement node.

This restores the configured two-replica requirement at the metadata and database level.


IMPORTANT ARCHITECTURE NOTE

This code completes database-level automatic re-replication.

At this prototype stage, replica creation is represented through PostgreSQL metadata records.

Once actual BOL node agents are running on separate machines, this database-only portion will be replaced by real communication with node agents.

The future production workflow will instruct the selected replacement node to:

- Download or receive the chunk
- Store the chunk physically
- Calculate and verify its checksum
- Confirm successful storage
- Report the completed operation to the control plane

Only after node-agent confirmation should production metadata be finalized.


7. Safety and Eligibility Rules Added

Automatic failover now prevents invalid promotion and replacement choices.

The system verifies:

- Replica node is online
- Replica node is not the failed node
- Replacement node is online
- Replacement node is not the promoted node
- Replacement node does not already hold the same replica
- Existing endpoint structure is reused
- No duplicate automatic-failover endpoint was introduced
